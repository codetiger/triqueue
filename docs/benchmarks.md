# Benchmarks

Completed measurements for the Tri-Queue core. Every table below is generated by a script in this repository, and the linked file holds the full data. This page only summarizes it.

**Scope.** Sections 1–4 are **utilization** results: useful MACs ÷ (peak MACs per cycle × cycles). Section 5 has area, clock frequency and energy after place and route at T = 8, for the engine only: the operand SRAM is not included yet, so the energy figures leave out the SRAM reads, which usually dominate at this size. Shapes come from `bench/workloads/gemm.csv`.

Further tables in the source file: shared read/write port (79.8% at 64³), drain hiding versus K, MAC command queue depth, and FIFO depth versus SRAM latency.

## 2. RTL, T = 8

Source: `verif/` (`make rtl-test`). The SystemVerilog core gives the same cycle count as the model for every one of 840 regression cases in 9 configurations (T = 4, 8, 16, 32; shared port; minimal queues; both accumulator forms; random memory back-pressure of 10–80%), including **4,130 cycles for 64³**. Results are bit-exact, and every memory transaction and MAC start happens on the same cycle as in the model.

## 4. Apple AMX reference (M2 Pro, measured)

Source: `bench/reference/amx/results.md` and `ablation.md`. AMX is fp32 at 256 MACs per cycle per unit, and the Tri-Queue figures are from the int8 cycle model at 64 MACs per cycle. Only utilization is compared, each against its own engine's measured peak.

| M×N×K | Tri-Queue (model) | AMX hand kernel | Accelerate sgemm, 1 thread |
| --- | --- | --- | --- |
| 32×32×32 | 93.8% | 31.5% | 7.8% |
| 64×64×64 | 99.2% | 78.3% | 33.5% |
| 256×256×256 | 100.0% | 91.0% | 74.3% |
| 512×512×512 | – | 93.1% | 86.9% |

**Accumulator double-banking (64×64×K), measured independently of precision:**

| K | AMX (1 accumulator, measured) | Tri-Queue, 1 bank | Tri-Queue, 2 banks |
| --- | --- | --- | --- |
| 8 | 16.8% | 30.5% | 46.0% |
| 16 | 39.9% | 46.7% | 91.3% |
| 32 | 62.2% | 63.7% | 98.4% |
| 128 | 81.5% | 87.5% | 99.6% |
| 1024 | 90.9% | 98.2% | 99.9% |

The second bank removes the per-tile drain stall that a production outer-product engine measurably pays. Spec §7.2 explains why this advantage depends on 1-cycle integer accumulation and doesn't carry over to floating point.

## 5. Place and route, T = 8

Source: `flow/results.md` (`flow/results.py`, from runs of `flow/ppa.py` and `flow/power.py`). OpenROAD-flow-scripts `d0e5b3c13`, typical corner, post-route STA and extracted parasitics. Power comes from simulating each workload in Verilator (checked against the model) with uniform random int8 operands, which switch more than real data. Engine only, without the operand SRAM. Energy is measured at the target clock, which post-route timing misses by 1–7%.

| | sky130hd, 100 MHz target | ASAP7, 1 GHz target |
| --- | --- | --- |
| Cell area | 0.948 mm² (252.5 kGE) | 14,319 µm² (245.5 kGE) |
| Flip-flops | 10,002 (156 per MAC) | 10,002 (156 per MAC) |
| Fmax (post-route) | 98.7 MHz | 933.6 MHz |
| Peak MACs/cycle per kGE | 0.253 | 0.261 |
| Energy per MAC, 64×64×64 (98.7% utilization) | 27.3 pJ | 1.12 pJ (1.79 TOPS/W) |
| Energy per MAC, ResNet-8 conv 256×32×288 (99.8%) | 26.6 pJ | 1.09 pJ (1.83 TOPS/W) |
| Energy per MAC, MobileNetV1 pointwise 2304×16×8 (46.8%) | 52.5 pJ | 2.20 pJ (0.91 TOPS/W) |

These figures are for the default plain 32-bit adder accumulator. Against the carry-save form, the plain adder uses 20–21% less cell area, 28% fewer flip-flops and 18–19% less energy per MAC, at the same clock within 1.3% (spec §10.2).

The clock tree and the registers draw 49–60% of the power, and they switch whether or not the array has work. At 47% utilization the engine still draws 91–94% of its full-utilization power, so energy per MAC roughly doubles.
