# Benchmarks

Completed measurements for the Tri-Queue core. The tables are generated by scripts in this repository (`model/results.md`, `model/dse.md`, `flow/results.md`, `bench/reference/amx/*.md`); this page is a hand-maintained summary. When a generated file changes, update the matching summary here. The linked file holds the full data.

**Scope.** Sections 1–4 are **utilization** results: useful MACs ÷ (peak MACs per cycle × cycles). Section 5 has area, clock frequency and energy after place and route at T = 8 and T = 16. The operand SRAM is outside `tq_top`, so engine-only figures are shown alongside a separate engine + SRAM line on sky130hd. Section 6 covers the Chipyard Rocket SoC run. Shapes come from `bench/workloads/gemm.csv`.

## 1. Cycle model, T = 8 (64 int8 MACs per cycle)

Source: `model/results.md` (`model/bench.py`). Memory latency 2, FIFO depth 8, separate write port. Every run is bit-exact against numpy.

| M×N×K | Cycles | Utilization | Limited by |
| --- | --- | --- | --- |
| 16×16×16 | 101 | 63.4% | Fixed 34-cycle start/end overhead |
| 32×32×32 | 546 | 93.8% | Fixed overhead |
| 64×64×64 | 4,130 | 99.2% | Nothing significant |
| 256×256×256 | 262,178 | 100.0% | Nothing significant |
| 60×60×60 | 3,859 | 87.5% | Edge tiles, K padded to 64 |
| 65×65×65 | 5,524 | 77.7% | 1-row/1-col remainder tiles, K padded to 72 |
| 1×512×512 | 24,593 | 16.7% | Matrix-vector: the read port caps it at 25% |

Further tables in the source file: shared read/write port (79.8% at 64³), drain hiding versus K, MAC command queue depth, and FIFO depth versus SRAM latency.

**Int8 output** (`MODE[2]`, shift-only). The drain writes one tile row per write instead of one port word of int32, so an int8 tile takes 8 writes instead of 16 at T = 8. On a separate port this takes 64³ from 99.2% to 99.4% and lifts 64×64×8 from 46.0% to 85.2% and 64×64×16 from 91.3% to 97.5%; on a shared port it lifts 64³ from 79.8% to 88.7%, 64×64×8 from 33.1% to 49.5% and 64×64×16 from 49.7% to 66.2% (`model/dse.md` §8). This is shift-only requantization, not a per-tensor scale.

**Int8 layer path** (`model/dse.md` §9, tag `layerpath`). The pointwise layer 2304×16×8 runs at 46.9% with int32 C and 88.5% with int8 C: C bytes fall 4× (147,456 → 36,864) but write transactions only 2× (9,216 → 4,608), so SRAM bytes per MAC halve (0.75 → 0.375). Batched decode (4×512×512) reaches 99.1% with a 4 KiB A-panel buffer and 8×512×512 reaches 99.9% without one; a batch-1 GEMV (1×256×K) stays at the 16.6–16.7% port-limited value until the buffer holds the whole panel — 24.6% with 4 KiB for K ≤ 1024, and 16 KiB is needed at K = 4096. The model does not charge for the host packing pass.

**Chaining output layout** (`model/dse.md` §10, model study only). Writing C in the next layer's A-panel order is bit-exact with the host packer and halves int8 write transactions again (4 words per tile at T = 8, against 8 for int8 rows and 16 for int32), removing activation repacking between layers. The default row-serial drain needs T−1 cycles before its first word, which is exposed at small K: 64×64×8 runs at 64.6% against 85.2% for int8 rows, and 2304×16×8 at 66.4% against 88.5%. A drain that snapshots the bank reaches 95.7% and 99.5%; at Kp ≥ 16 the layout is free either way.

**Epilogue delivery** (`model/dse.md` §11). Per-tensor scale and a bias adder in the drain lane cost no cycles; a per-column bias plus 16-bit scale delivered as a per-tile stream is 3 port words per tile (+37% of the operand traffic at Kp = 8), so per-column metadata wants a table. Bias as an extra k step costs a whole 8-step padding panel when K is a multiple of 8: 64×64×8 85.2% → 54.9%, 2304×16×8 88.5% → 56.1%; it is free when K mod 8 ≠ 0.

## 2. RTL, T = 8

Source: `verif/` (`make rtl-test`). The SystemVerilog core gives the same cycle count as the model for every one of **1,709 regression cases in 25 configurations** (T = 4, 8, 16, 32; shared port; minimal and reference queues; both accumulator forms; panel buffer; single-beat and burst AXI; CV-X-IF; and random memory back-pressure of 10–80%), including **4,130 cycles for 64³**. Results are bit-exact, and every memory transaction and MAC start happens on the same cycle as in the model. See [`docs/verification.md`](verification.md) for the matrix and the known coverage gaps.

## 5. Place and route, T = 8 and T = 16

Source: `flow/results.md` (`flow/results.py`, from runs of `flow/ppa.py` and `flow/power.py`). OpenROAD-flow-scripts `d0e5b3c13`, typical corner, post-route STA and extracted parasitics. Power comes from simulating each workload in Verilator (checked against the model) with uniform random int8 operands, which switch more than real data. Reference configuration: plain-adder accumulator, clock gating on, operand FIFOs of depth 4 and a 3-entry MAC command queue (enough for an SRAM with up to 3 cycles of read latency, with no cycle lost). Engine only unless stated.

| | sky130hd, T = 8 (100 MHz, 55% util) | ASAP7, T = 8 (1 GHz, 70% util) | ASAP7, T = 16 (741 MHz, 70% util) |
| --- | --- | --- | --- |
| Cell area / core area | 0.693 mm² / 1.110 mm² (184.6 kGE) | 10,281 µm² / 13,820 µm² (176.3 kGE) | 33,340 µm² / 45,785 µm² (571.7 kGE) |
| Post-route stdcell density | 62.4% (100.0% row fill) | 74.4% (100.0% row fill) | 72.8% |
| Flip-flops | 8,562 (134 per MAC) | 8,562 (134 per MAC) | 25,544 (100 per MAC) |
| Fmax (post-route) | 99.9 MHz (-14 ps slack) | 992.5 MHz (-8 ps slack) | 762.2 MHz (closes 741 MHz) |
| Peak MACs/cycle per kGE | 0.347 | 0.363 | 0.448 |
| Energy per MAC, 64×64×64 (98.6% / 93.1% util) | 16.9 pJ (0.119 TOPS/W) | 0.69 pJ (2.91 TOPS/W) | 0.67 pJ (2.98 TOPS/W) |
| Energy per MAC, ResNet-8 conv 256×32×288 (99.8% / 99.2%) | 16.4 pJ (0.122 TOPS/W) | 0.67 pJ (3.00 TOPS/W) | 0.64 pJ (3.14 TOPS/W) |
| Energy per MAC, MobileNetV1 pointwise 2304×16×8 (46.8% / 24.0%) | 25.3 pJ (0.079 TOPS/W) | 1.08 pJ (1.85 TOPS/W) | 1.28 pJ (1.57 TOPS/W) |
| Geometric mean of the three | 19.1 pJ (0.105 TOPS/W) | 0.79 pJ (2.53 TOPS/W) | 0.82 pJ (2.45 TOPS/W) |
| ResNet-8 conv with ReLU-like operands (synthetic, half-zero activations) | 13.9 pJ (0.144 TOPS/W) | 0.58 pJ (3.47 TOPS/W) | 0.54 pJ (3.70 TOPS/W) |
| Engine + operand SRAM, geometric mean (OpenRAM macro, sky130 only) | 23.7 pJ (0.084 TOPS/W) | – | – |

- **Clock gating** (`CLK_GATE = 0` for comparison) cuts power by 24–40%, cell area by 8.5% and energy per MAC by 29.9% (sky130hd; ASAP7: 21–34%, 6.7% and 25.7%), at essentially the same clock. The relative power saving is larger at lower utilization because the gated clock trees and registers stop switching. What remains is mostly the multiplier array's switching, which follows the operand data; operand isolation on idle and unused quadrants is the next power lever (spec §11).
- **Accumulator form:** against carry-save, the plain adder uses 23.4% less cell area, has 31.7% fewer flip-flops and uses 21.6% less energy per MAC on sky130hd (ASAP7: 18.4%, 31.7%, 18.0%), at a slightly higher clock (spec §10.2).
- **SRAM line:** each workload's reads and writes times the access energy of ORFS's OpenRAM macro `sky130_sram_1rw1r_128x256_8` (179 pJ per access from its liberty, which charges every clock edge the same), plus leakage; it adds 3.0–8.4 pJ per MAC. ASAP7 has only placeholder SRAM models, so it has no SRAM line.

## 6. SoC integration (Chipyard Rocket)

Source: `bench/soc/chipyard/README.md`. A one-core Rocket SoC (Chipyard 1.15.0) with `tq_top_axi` attached to the periphery and front buses, running a 64×64×64 int8 GEMM in Verilator through `sw/tq.c`.

It passes with 0 mismatches and the same 4,096 beats, 4,096 reads and 1,024 writes as the cycle model, in **38,295 cycles (10.6% utilization)** against 4,130 cycles (99.2%) on a 2-cycle SRAM. This run is from 2026-11-08 (`65815f3`); it predates the driver's GEMM API (`261d12d`) and the v1 RTL (`cfd68f4`), and has not been re-run since. The 8-word operand FIFOs are meant for tightly coupled SRAM and do not hide the latency of the TileLink-to-AXI bridge, L2 cache and DRAM. This is a memory-latency result, not a core limit: the supported v1 integration is a low-latency SRAM or TCM. A deeper FIFO, read bursts and the optional panel buffer are the levers for a cached-memory SoC; no measured profile for that exists yet (`docs/integration.md`).
