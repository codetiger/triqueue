# Tri-Queue: a simple matrix coprocessor for RISC-V

An open-source int8 matrix-multiply coprocessor in SystemVerilog for RISC-V SoCs, inspired by Apple's AMX, Arm SME and UC Berkeley's Gemmini.

Like AMX and SME, it computes outer products into an in-place output tile. Like Gemmini, it uses decoupled queues so loads and stores overlap compute. To stay small and simple, it drops the vector register file, the operand crossbar and the scratchpad SRAM: the whole datapath is two operand FIFOs (`QA`, `QB`) feeding a double-banked `T × T` int32 accumulator tile (`SC`), driven by a 10-byte hardware-looped program. On edge and corner tiles where half the rows or columns would otherwise sit idle, **variable-arity accumulate cells** (`r × c × d = T²`) put the spare multiplier quadrants to work on extra `k` steps in the same cycle, lifting edge-tile utilization from 50% to 67% and corner tiles from 25% to 50% with fixed quadrant wiring (`docs/specification.md` §4).

**Status:** v1.0.0. The SystemVerilog core matches the Python reference model cycle for cycle and is bit-exact against numpy across 1,709 test cases in 25 configurations. Formal proofs (SymbiYosys) cover the FIFOs, clock-gating cells, bus adapters and the `T = 4` core. It attaches through AXI4-Lite, AXI4 (single-beat or read-burst) or CV-X-IF adapters, writes int32 or shift-only int8 results, has a bare-metal C driver, and runs a GEMM on a Chipyard Rocket SoC. See [`docs/integration.md`](docs/integration.md) for the SoC contract and [`CHANGELOG.md`](CHANGELOG.md) for the v1 scope. All PPA comparison records in `flow/results.md` are re-recorded at one RTL commit; the same-commit layout bundle is locked as `v1.0.0`.

At `T = 8` (64 int8 MACs/cycle), the core has been placed and routed with OpenROAD on sky130hd and ASAP7, with power from simulated workload activity:
- **sky130hd (100 MHz target, 99.9 MHz post-route, 55% core util):** 0.69 mm² cell area / 1.11 mm² core (185 kGE), 8,562 flip-flops, 16.4–25.3 pJ per MAC (19.1 pJ geometric mean, engine only), or 23.7 pJ geometric mean including an OpenRAM operand macro.
- **ASAP7 (1 GHz target, 992.5 MHz post-route, 70% core util):** 10,281 µm² cell area / 13,820 µm² core (176 kGE), 0.67–1.08 pJ per MAC (0.79 pJ / 2.53 TOPS/W geometric mean, engine only).

See [`docs/benchmarks.md`](docs/benchmarks.md) for the full results.

## Why

Open matrix engines exist, but they are hard to compare: each is evaluated in its own flow, on its own workloads, at its own process node. Most are also tied to one SoC generator. This project aims to provide:

1. **A small, efficient engine.** Near-peak utilization on matrix multiply without a register file or scoreboard. At `T = 8` it reaches 99.2% of peak on 64³ int8 GEMM with about 6.5 Kbit of architectural state (8,562 flip-flops in total with the reference queues).
2. **Easy integration.** A parameterized core (`T = 4, 8, 16, 32`) that does not depend on any SoC generator, with thin adapters for AXI4-Lite, AXI4 and CV-X-IF, plus a freestanding C driver.
3. **Fair, reproducible benchmarks.** The same workloads, open PDKs and synthesis flow for this design and other open designs, with every measured number generated by a script in the repo and each summary linking to the generated file.

## Scope and limitations

To keep the hardware simple and the numbers honest, several boundaries are fixed up front:

- **int8/uint8 inputs, int32 or int8 outputs.** There is no floating-point support. The int8 output mode is a saturating arithmetic shift (`MODE[7:3]`), not a full per-tensor/per-channel requantization; there is no bias or activation. Hiding tile drain behind compute with just two accumulator banks relies on 1-cycle integer accumulation (`docs/specification.md` §7.2).
- **Built for fast local SRAM.** The operand FIFOs hide a few cycles of SRAM read latency, not cache misses or DRAM. Attached directly to cached DRAM over TileLink in a Chipyard Rocket SoC, a 64³ GEMM still passes bit-exact, but utilization drops from 99.2% to 10.6% (38,295 vs 4,130 cycles). That path is supported for correctness, not as a performance point.
- **Pre-packed operands.** The host or DMA packs `A` into column panels and `B` into row panels before a run (`sw/tq.c` includes the packer). Without the optional `A` panel buffer, panels are re-read from SRAM for each output tile. The panel buffer is experimental and defaults off.
- **GEMM only.** There are no built-in activation, bias or per-tensor scale stages, and narrow matrix-vector (`M = 1`) shapes are capped at 25% by read-port bandwidth. Same-flow comparisons against Gemmini and RVV are still in progress.
- **Memory contract.** A, B and C must not overlap; the core is not coherent with host caches; no host writes during a run. See [`docs/integration.md`](docs/integration.md).

## Design priorities

In order of importance:

| Priority | Metric |
| --- | --- |
| Performance per watt | Useful int8 ops per joule (TOPS/W) on real workload shapes, not peak |
| Performance per component | Useful MACs/cycle per mm² and per kGE; state bits per MAC |
| Design reusability | Parameterized core, standard interfaces, no dependency on a particular SoC generator |
| Overall efficiency | Utilization across a workload suite, including small, edge-tile and GEMV shapes |

Peak throughput is a parameter, set by tile size and port width. It is not a goal in its own right.

## Quick start

Python 3.10+ and a C compiler are enough to run the cycle model and C driver tests. RTL targets also need Verilator 5, Yosys, SymbiYosys and Yices:

```sh
git clone https://github.com/codetiger/triqueue.git && cd triqueue
pip install -r requirements.txt

make model-test sw-test   # Python model + C driver tests (~5 s, no EDA tools needed)
make                      # full check: model, driver, SPDX, lock, RTL lint, RTL regression, formal, synth check
make -C sw                # build the C driver as a static library
make dist                 # release tarball, golden-vector set and SHA256SUMS
make ui-serve             # open the interactive visualizer at http://localhost:8080
```
