# Apple AMX (M2 Pro) vs Tri-Queue: utilization

Generated by `bench/reference/amx/compare.py` from measurements on this machine. AMX is undocumented; the kernels use the encodings from github.com/corsix/amx.

## AMX hand kernel breakdown (fit over 64×64×K)

- Steady state: 4.31 AMX cycles per k step for 4 fma32 → **92.9%** of peak.
- Fixed cost per 32×32 output tile: ≈ **95 cycles**, which is the single Z accumulator's 64 stores plus per-call overhead spread over the 4 tiles.
- See `ablation.md` for a 3-parameter fit that separates per-call from per-tile cost.

## Caveats

- **Same bytes per MAC, different reuse per element.** AMX's 32×32 fp32 tile does 16 MACs per element loaded and the Tri-Queue's 8×8 int8 tile does 4, but both read 0.25 bytes per MAC.
- **Different precisions and sizes.** AMX does 256 fp32 MACs per cycle per unit, and the Tri-Queue does 64 int8 MACs. Only utilization is compared, not throughput or efficiency.
- **Model vs silicon.** The Tri-Queue numbers assume ideal SRAM with fixed latency. AMX numbers are real hardware fed from L1/L2 caches, with OS noise and clock variation.
- **Accelerate includes CPU-side packing and call overhead,** about 0.4 µs per call, which dominates small GEMMs. The hand kernel and the Tri-Queue model both exclude packing.
- **Accelerate only goes multi-threaded from about 512³.** Below that, the all-threads column is low because its denominator is every AMX unit on the chip.
- **The hand kernel is straightforward, not expert-tuned.** Z holds exactly one 32×32 fp32 tile, so its store can't overlap compute unless the tile shrinks (for example to two 32×16 halves taking turns), which lowers reuse. A tuned kernel could narrow the small-size gap.
- **GEMV is memory-bound everywhere.** For example, 1×4096×4096 in Accelerate runs at 5.8 GMAC/s, which is about 23 GB/s of fp32 matrix streaming from DRAM.
